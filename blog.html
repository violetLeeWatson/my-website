逐项解释 docusaurus.config.ts 中的配置项

逐项解释 docusaurus.config.ts 中的配置项。

Config Overview

  • title: 网站主标题，显示在浏览器标签、导航栏等位置。
  • tagline: 站点副标题/口号，用于首页和社交分享卡文案。
  • favicon: 浏览器标签的小图标路径（通常放在 static 下）。
  • future.v4: 启用 Docusaurus v4 的未来兼容/实验性特性开关。
  • url: 网站的主域名（用于生成绝对链接和 Open Graph URL）。
  • baseUrl: 部署在域名下的子路径（例如 GitHub Pages 的仓库名，通常以 / 结尾）。
  • deploymentBranch: 部署时推送静态文件的分支（默认 gh-pages）；用于 GitHub Pages 部署。
  • trailingSlash: 是否在生成的 URL 末尾保留斜杠，false 常用于去掉末尾斜杠。
  • organizationName: GitHub 用户或组织名，常用于生成仓库相关链接与部署配置。
  • projectName: 仓库名，配合 organizationName 用于部署和生成某些自动链接。
  • onBrokenLinks: 断链处理策略（'throw'：构建失败；'warn'：仅提示）。
  • i18n.defaultLocale / i18n.locales: 默认语言与可用语言列表，影响 HTML lang、路径前缀和语言切换。
  • presets: 预设集合，这里用 'classic'，包含 docs、blog、theme 的默认配置和扩展点。
  • presets[classic].docs.sidebarPath: 指向侧边栏配置文件（侧边栏如何组织文档）。
  • presets[classic].docs.editUrl: “Edit this page” 链接前缀，建议改为你自己的仓库 URL 以启用编辑链接。
  • presets[classic].blog.showReadingTime: 是否在文章中显示预计阅读时间。
  • presets[classic].blog.feedOptions: 博客 feed（RSS/Atom）输出配置，例如生成哪些格式。
  • presets[classic].blog.onInlineTags / onInlineAuthors / onUntruncatedBlogPosts: 博客内容校验/策略（如发现问题时警告）。
  • presets[classic].theme.customCss: 自定义 CSS 路径，用于覆盖或补充默认样式。
  • themeConfig.image: 默认的社交分享/卡片图片（Open Graph/Twitter Card）。
  • themeConfig.colorMode.respectPrefersColorScheme: 是否尊重用户系统的深色/浅色主题偏好。
  • themeConfig.navbar: 导航栏设置（title、logo、items）。items 中可用 type: 'docSidebar'（链接文档侧边栏）、to（站内路由）、href（外部链接）等。
  • themeConfig.footer: 页脚配置（style、多列 links、版权文本等）。
  • themeConfig.prism.theme / darkTheme: 代码高亮主题，分别用于浅色与深色模式（这里使用 prism-react-renderer 的主题）。
  • TypeScript typings: 使用 Config 类型和 satisfies Preset.Options/ThemeConfig 只是为了编辑时的类型检查与自动完成，不改变运行时行为。
  • export default config: 导出配置对象，Docusaurus 在构建时读取它来生成站点。

逐项解释 docs/myname/category.json 中的配置项

下面是 category.json 各字段的简明解释及可选修改建议：

  • label: 在文档侧边栏中显示的分类名称（本例为 "Tutorial - Basics"）。
    建议：改为更贴合 docker 内容的名称，比如 "Docker 教程" 或 "Docker 入门"，以提高语义清晰度。

  • position: 在同级分类或侧边栏中排序的位置，数值越小越靠前（本例为 2）。
    建议：根据侧边栏中其它分类的 position 值调整顺序；如果不需要显式控制，可移除。

  • link: 定义当用户点击该分类时导航到的页面。常见 type 有 doc、generated-index 等。

    • type: "generated-index"：表示自动生成一个分类索引页面，列出该分类下的文档，并使用 description（下面字段）作为索引页说明。
    • description: 自动索引页上显示的一段描述文本（本例为 "5 minutes to learn..."）。
      建议：把 description 改为中文或更具体的介绍，例如 "本分类包含 Docker 基础教程与示例。"；如果你已有专门的入门文档文件，也可以用 type: "doc" 并设置 id 指向该文档。

github的fork操作_自用

June 22, 2026 · 5 min read

0## 如何使用

你可以直接 fork 或 clone 本仓库并按原样使用。

✨ 它可以开箱即用。 ✨

在私有仓库中使用​

如果你想使用私有仓库，GitHub 不允许直接 fork 并修改可见性，但你可以：

  • 创建一个新的 GitHub 仓库，例如 my-full-stack。
  • 手动克隆本仓库，并把目标目录命名为你想要的项目名，例如 my-full-stack：
git clone git@github.com:fastapi/full-stack-fastapi-template.git my-full-stack
  • 进入新目录：
cd my-full-stack
  • 将新的远程仓库地址设置为你的仓库（从 GitHub 拷贝）：
git remote set-url origin git@github.com:octocat/my-full-stack.git
  • 添加原模板仓库为另一个远程，以便日后获取更新：
git remote add upstream git@github.com:fastapi/full-stack-fastapi-template.git
  • 推送代码到你的仓库：
git push -u origin master

从原始模板更新​

克隆并修改后，若想从模板获取最新改动：

  • 确保已把原仓库添加为 upstream 远程。
git remote -v

origin    git@github.com:octocat/my-full-stack.git (fetch)
origin    git@github.com:octocat/my-full-stack.git (push)
upstream    git@github.com:fastapi/full-stack-fastapi-template.git (fetch)
upstream    git@github.com:fastapi/full-stack-fastapi-template.git (push)
  • 拉取最新改动但不自动合并提交：
git pull --no-commit upstream master

这会下载最新改动但不自动提交，让你先检查再合并。

  • 若出现冲突，请在编辑器中解决冲突。
  • 解决完成后提交更改：
git merge --continue

这是github上开源项目的使用readme文档的一部分，能解释一下吗

解释

当然可以！这段文字来自一个 GitHub 上的开源项目（fastapi/full-stack-fastapi-template），它是一个 全栈 FastAPI 项目模板。下面我将逐段为你详细解释其含义和操作逻辑。

📌 总体目标​

这段文档教用户：

  1. 如何 基于该模板创建自己的项目（尤其是私有项目）；
  2. 如何 保留与原始模板的联系，以便未来能同步官方更新。

🔹 第一部分：基本使用方式​

你可以直接 fork 或 clone 本仓库并按原样使用。✨ 它可以开箱即用。✨

  • Fork：点击 GitHub 上的 “Fork” 按钮，把项目复制到你自己的账号下（变成 yourname/full-stack-fastapi-template）。
  • Clone：用 git clone 把代码下载到本地。
  • 这个模板已经配置好了前后端、Docker、数据库等，无需额外设置就能运行（“开箱即用”）。

✅ 适合公开项目或不想改名的情况。

🔹 第二部分：在私有仓库中使用（重点！）​

GitHub 不允许你 fork 一个公开仓库后直接改成私有（这是平台限制）。所以如果你想要一个私有的、可自定义名称的项目，需要手动操作：

步骤详解：​

1. 创建一个新的私有仓库​

  • 在 GitHub 上新建一个空仓库，比如叫 my-full-stack（设为私有）。

2. 克隆原始模板，并重命名本地文件夹​

git clone git@github.com:fastapi/full-stack-fastapi-template.git my-full-stack
  • 这会把模板代码下载到名为 my-full-stack 的文件夹中（而不是默认的 full-stack-fastapi-template）。

3. 进入新目录​

cd my-full-stack

4. 修改远程仓库地址（关键！）​

git remote set-url origin git@github.com:octocat/my-full-stack.git

git remote set-url origin git@github.com:violetLeeWatson/my-fullstack.git

  • 原本 origin 指向官方模板仓库。
  • 这条命令把它改成你自己的私有仓库地址（octocat 是你的 GitHub 用户名）。
  • ✅ 现在 git push 会推送到你的私有仓库，而不是官方模板！

5. 添加原始模板为 upstream（用于后续更新）​

git remote add upstream git@github.com:fastapi/full-stack-fastapi-template.git
  • upstream 是一个约定俗成的名字，表示“上游源”。
  • 这样你以后还能从官方模板拉取新功能或修复。

6. 首次推送代码到你的私有仓库​

git push -u origin master
  • -u 表示设置默认推送分支，以后只需 git push 即可。

🔹 第三部分：如何从原始模板获取更新​

即使你已开始开发自己的项目，仍可能想同步官方模板的新特性（比如安全修复、新功能）。

操作流程：​

1. 确保 upstream 已设置​

git remote -v

应看到 origin（你的仓库）和 upstream（官方模板）。

2. 拉取官方最新代码（但不自动合并）​

git pull --no-commit upstream master
  • --no-commit 很重要！它会把改动“应用”到工作区，但不自动提交。
  • 这样你可以先检查哪些文件被修改，避免意外覆盖你的代码。

3. 手动解决冲突（如有）​

  • 如果你修改了某些文件，而官方也改了同一处，Git 会标记 冲突（conflict）。
  • 你需要用编辑器打开这些文件，选择保留哪部分代码。

4. 提交合并结果​

git merge --continue
  • 解决完所有冲突后，执行此命令完成合并并提交。

💡 小技巧：也可以用 git merge upstream/master，但 pull --no-commit 更安全，适合新手。

✅ 总结：这套流程的优点​

目标实现方式
使用官方模板git clone
项目私有化 + 自定义名称手动创建私有仓库 + git remote set-url
保留更新能力添加 upstream 远程
安全合并更新git pull --no-commit + 手动检查

这种模式是 开源模板项目的标准实践，广泛用于 Next.js、React、FastAPI 等脚手架项目。你既享受了模板的便利，又拥有完全的控制权。

怎么部署到 GitHub Pages

June 21, 2026 · 5 min read

当然可以！以下是将你提供的内容转换为标准、安全的 Markdown 语法后的版本，已特别注意：

  • 所有花括号 {} 都已转义（\{ 和 \}）或放入代码块中
  • 避免任何可能被 Docusaurus/MDX 解析为 JSX 表达式的结构
  • 使用标准的 Markdown 标题、列表、代码块语法
  • 适用于 .md 博客文件（如 Docusaurus）

我在 GitHub 上使用 **Build and deployment → Source → Branch** 方式时，只能选择两个文件夹：`/(root)` 和 `/docs`，但我构建好的静态资源在 `/build` 下，怎么办？

你遇到的问题非常典型：**GitHub Pages 默认只允许从 `/(root)` 或 `/docs` 目录发布网站**，但 Docusaurus（或其他框架）构建的静态文件默认输出到 `/build` 文件夹，导致无法直接选择。

别担心！有 3 种主流解决方案，推荐按顺序尝试：

---

### ✅ 方案 1：【最推荐】改用 `gh-pages` 分支部署（自动推送 `/build` 内容）

这是 Docusaurus 官方推荐的方式，**完全绕过 GitHub Pages 对目录的限制**。

#### 步骤如下：

1. **安装 `gh-pages` 工具**
   ```bash
   npm install --save-dev gh-pages

  1. 在 package.json 中添加部署脚本

    {
      "scripts": {
        "build": "docusaurus build",
        "deploy": "docusaurus deploy"
      }
    }

  2. 在 docusaurus.config.js 中配置部署信息

    module.exports = {
      // 必须设置 url 和 baseUrl
      url: 'https://你的用户名.github.io',
      baseUrl: '/你的仓库名/', // 注意：如果是用户主页（<用户名>.github.io），这里应为 '/'

      // ... 其他配置

      // 添加部署配置（可选，新版 Docusaurus 可自动推断）
      deploymentBranch: 'gh-pages', // 默认就是 gh-pages
      trailingSlash: false,
    };

  3. 运行部署命令

    # 设置 Git 用户名（首次需配置）
    git config --global user.email "你的邮箱"
    git config --global user.name "你的用户名"

    # 部署（会自动构建 + 推送到 gh-pages 分支）
    npm run deploy

  4. 在 GitHub 仓库中启用 gh-pages 分支作为源

    • 进入仓库 → Settings → Pages
    • 在 Source 处选择：
      • Branch: gh-pages
      • Folder: /(root)
    • 点击 Save

✅ 几分钟后，你的网站就会通过 https://<用户名>.github.io/<仓库名> 访问！

📌 优点：自动化、安全、不污染主分支、支持自定义域名。

✅ 方案 2：将构建输出改为 /docs 目录（适合简单项目）​

如果你不想用新分支，可以让 Docusaurus 把文件生成到 /docs，这样就能直接选 /docs 作为 Pages 源。

修改 docusaurus.config.js：​

module.exports = {
  // 将输出目录改为 docs
  staticDirectories: ['static'],
  // 👇 关键配置
  onBuildSuccess: () => {
    const fs = require('fs');
    const path = require('path');
    const shell = require('shelljs');

    // 构建完成后，把 build 内容复制到 docs
    shell.rm('-rf', 'docs');
    shell.cp('-r', 'build/*', 'docs/');
    console.log('✅ Copied build output to /docs');
  },

  // 或者更简单：直接修改构建输出路径（Docusaurus v3 支持）
  // 但官方不推荐，所以用上面的 hook 更稳妥
};

或者更简单的做法（无需改代码）：

# 手动复制（每次构建后执行）
npm run build
rm -rf docs
cp -r build docs
git add docs
git commit -m "Update docs for GitHub Pages"
git push

然后在 GitHub Pages 设置中选择：

  • Branch: main（或你的主分支）
  • Folder: /docs

⚠️ 缺点：/docs 目录会混入源码，Git 历史变乱。

✅ 方案 3：使用 GitHub Actions 自动构建并部署到 gh-pages（高级）​

适合 CI/CD 场景，每次 push 自动部署。

在 .github/workflows/deploy.yml 创建：

name: Deploy to GitHub Pages

on:
  push:
    branches: [ main ]  # 你的主分支名

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci
      - run: npm run build

      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v4
        with:
          github_token: ${{ secrets.GITHUB_TOKEN }}
          publish_dir: ./build

✅ 推送后，Action 会自动构建并将 ./build 内容推送到 gh-pages 分支。

然后在 Settings → Pages 中选择 gh-pages 分支即可。

📌 总结：如何选择？​

方案难度推荐度适用场景
gh-pages 分支 + npm run deploy⭐⭐⭐⭐⭐⭐⭐所有 Docusaurus 用户首选
输出到 /docs⭐⭐⭐快速测试、不想新建分支
GitHub Actions⭐⭐⭐⭐⭐⭐⭐团队协作、自动化需求

🔥 强烈建议你用 方案 1（gh-pages 分支）​

只需 3 条命令：

npm install --save-dev gh-pages
# 确保 docusaurus.config.js 配置了 url 和 baseUrl
npm run deploy

然后去 GitHub Pages 设置里选 gh-pages 分支，搞定！

# 推荐操作流程（首次部署）

## 1. 构建网站（确保有 build/ 目录）
npm run build

## 2. 首次部署：用 gh-pages 手动推送一次（自动创建分支）
npx gh-pages -d build

## 3. 之后就可以正常使用 deploy 了
npm run deploy
✅ 只需第 2 步做一次，以后都用 npm run deploy 即可。
